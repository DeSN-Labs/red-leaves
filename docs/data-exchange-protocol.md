# 数据交换协议 v0.1 讨论稿

日期：2026-10-16

## 1. 范围与状态

本文记录已确认的用户常驻服务注册、NAS 定位和权限更新规则，保留社交数据交换的设计入口。“已确认”表示设计决定，不表示已实现或部署。本文不是最终合约 ABI、网络报文或密码协议规范。

节点间通信及中继参与的第一版规格见 [NAS 节点通信协议 v0.1 草案](node-communication-protocol-v0.1.md)。共享库已提供消息、编解码、签名与完整性校验原型，具体编码和实现边界见 [protocol 说明](../crates/protocol/README.md)；NAS 已通过独立的 delivery v2 接入直连／配置中继、范围推送及私密内容加密，见[推送说明](scoped-delivery.md)；本文完整的服务授权／撤销及自动发现仍未实现，待定项不因消息类型存在而自动完成。

产品依据见[产品需求规格说明书](product-requirements.md)，主要关联 FR-010～019、FR-020～028、FR-030～044。未确定的字段和行为不得视为开发定案。

## 2. 网络与身份边界（已确认）

当前所有链上功能使用 Base Sepolia，Chain ID 为 `84532`。身份注册先行，测试代币、打赏及中继结算仍按后续排期开发，不将帖子、点赞和收藏默认上链。NAS 通过可配置 RPC 访问链，不要求运行 L2 验证全节点；对 RPC 存在信任依赖，故障切换策略待定。

长期自建 L2、发行代币为后续方向，技术栈及迁移规则未定。更换 RPC 不等于完成身份、授权和资产迁移。部署与更新需要测试 ETH 支付 gas；NAS 服务密钥可以持有少量测试 ETH，但不获得用户钱包资金控制权。

| 身份／密钥 | 职责 | 权限边界 |
| --- | --- | --- |
| 用户钱包 | 用户身份及绑定控制者 | 绑定、更换、撤销常驻服务；私钥不交给 NAS |
| App 设备密钥 | 经授权签署帖子及用户行为 | 设备授权另行设计，不能由 NAS 服务权限代替 |
| NAS 节点密钥 | 证明连接对端节点身份 | 不代表节点上所有用户，不授予用户行为签名权 |
| 每用户 NAS 服务密钥 | 投递、同步、更新入口 | 不得签署用户帖子、支配用户钱包资金或授权新设备 |

同一 NAS 可服务多个家庭成员，节点身份可以共用，每个用户的服务密钥及授权独立。钱包地址不等于加密公钥；服务签名密钥也不自动作为内容解密密钥。

用户应用密钥特指内容加密／解密密钥对：公钥登记到链上 `encryptionPublicKey` 字段，私钥由用户信任的 NAS 盒子按用户独立保管。NAS 可主动使用该私钥解密针对对应公钥加密的获授权内容或内容密钥，客户端离线时也可处理。该决定不包括钱包私钥或设备签名私钥，不赋予 NAS 用户行为签名权或发布确认权，也不混用 NAS 服务签名密钥。私钥不得通过普通 API 返回、写入日志、公开传播或上链；本地文本原型已接入 NAS 持钥、加密文件保管及公钥查询，Web 首次登记改用 NAS 公钥；旧浏览器私钥不会自动迁移，备份／恢复仍需手工保留文件，见[发帖说明](posting.md)。

## 3. 链上用户注册记录（已确认）

按钱包地址查询所配置网络的注册合约。网络和合约地址共同限定注册表，不能将任意同名合约视为权威。

链上用户信息仅包含以下四项，替代旧草案将服务密钥、中继入口及入口序号登记上链的方案：

| 字段 | 概念类型 | 含义与控制者 |
| --- | --- | --- |
| `owner` | 钱包地址 | 查询键和用户身份，控制本人登记信息 |
| `nasPeerId` | 节点身份标识 | 对应常驻 NAS 的 P2P 身份，由用户钱包设置；不是家庭 IP 或固定网络入口 |
| `encryptionPublicKey` | 内容加密公钥 | 完整公钥直接登记，由用户钱包控制；不是钱包地址或 NAS 服务签名密钥 |
| `nickname` | 昵称 | 公开昵称，由用户钱包控制；首版限制 1～128 字节，允许重名，客户端使用 UTF-8 |

头像、性别及其他资料不上链，通过 NAS／P2P 网络获取。头像文件、地址、内容标识及校验哈希均不作为链上资料字段。链下资料按用户可见范围提供，网络获取不等于公开广播。

中继入口、每用户 NAS 服务授权及其版本信息改为链下设计，不默认登记到合约。具体发布、发现、签名、钱包授权、防重放和撤销方案待定，不得直接信任网络返回的地址或服务密钥。

不登记家庭内网地址、家庭 IP、私钥、访问令牌或明文内容密钥。链上记录及其历史公开可查询。字段是语义定义，不是最终 Solidity 类型；`contracts/src/UserRegistry.sol` 已实现首版注册与单字段更新，部署证据及核验状态见 [部署记录](../contracts/deployments/base-sepolia.json)；接口及实现边界见 [合约说明](../contracts/README.md)。

首版公钥字段必填，校验 1～256 字节的长度；算法、编码、版本及轮换／撤销规则、多设备密钥和恢复流程仍待设计。对应私钥不得上链或公开传播；NAS 投递权限不能扩大为公钥或昵称修改权限。

## 4. 用户登记操作与权限

已确认：用户钱包控制本人的 NAS 绑定、内容加密公钥和昵称，NAS 服务密钥不得代替钱包更改这些登记。

| 操作 | 语义 | 待定事项 |
| --- | --- | --- |
| 首次登记 | 钱包建立本人的四项注册信息 | 首版三个资料字段均非空；PeerId／昵称最多 128 字节，公钥最多 256 字节，超限抛出对应自定义错误 |
| 更换 NAS | 钱包更新本人 `nasPeerId` | 旧服务授权失效、链下路由及缓存刷新规则 |
| 更新公钥 | 钱包更新本人内容加密公钥 | 旧密文解密、密钥版本及撤销规则 |
| 修改昵称 | 钱包更新本人昵称 | 首版 1～128 字节且允许重名；UTF-8 有效性和规范化由客户端处理 |
| 撤销绑定 | 钱包撤销本人的 NAS 绑定 | 记录表达、防旧记录重放及重新绑定规则 |
| 查询 | 读取注册记录，不改变状态 | 首版 `getUser` 返回三个资料字段，缺失记录抛出 `NotRegistered`，另提供 `isRegistered` 查询 |

旧草案中的链上 `serviceKey`、`generation`、`active`、`relayEndpoints`、`endpointRevision` 不再视为已确认字段；如后续需要额外的技术状态，须另行确认，不能据此自行扩展上述四项范围。

## 5. 从钱包地址定位 NAS

1. 查询指定链和注册合约，读取用户 NAS PeerId、公钥及昵称；读取失败不能解释为用户未注册。
2. 根据 NAS PeerId 从链下网络获取连接线索。中继入口的发现与认证协议待定，不能仅凭 PeerId 承诺 NAS 可达。
3. 有已验证直连通道时可尝试直连，否则通过经验证的中继入口连接。NAS 主动连接中继，不要求家庭公网入站地址。
4. 验证对端持有登记 PeerId 对应的节点身份，并验证当前用户与 NAS 的服务授权。具体挑战证明、会话绑定和链下授权报文待定。
5. 验证通过后获取链下资料或交换受保护数据；头像、性别等资料的来源、版本和访问权限也须验证。App 与自己的 NAS 端到端加密，中继不能代替 NAS 证明身份。
6. 失败时刷新链上登记及链下连接线索，仍失败报告不可达，不将登记成功解释为在线。

用户发现以钱包地址和链上 NAS PeerId 为起点；不依赖面对面扫码或用户链接。设备首次配对另行设计。链下发现的具体协议尚未实现。

## 6. 链状态、缓存与撤销传播

提交交易不等于成功执行；执行成功也不代表所有节点刷新缓存。更换或撤销 NAS 后，旧授权的识别、链下撤销传播和历史记录防重放机制仍需设计，不能沿用旧草案的链上入口更新流程作为已确认实现方案。

撤销服务绑定不能删除已合法传播的帖子。链上不可读取时，不能把旧缓存宣称为最新授权或默认接受新绑定。

待定：确认策略、读取区块信息、缓存期限、敏感操作刷新策略、链重组回滚、RPC 分歧、合约地址分发及迁移、历史签名有效性。未确定前不承诺完整实时撤销或最终性保障。

公钥轮换的候选规则：每次为接收者建立新的内容密钥封装前，重新读取指定合约的公钥；读取失败暂停，不回退到旧缓存。读取需记录区块号／哈希及公钥指纹，确认和重组策略另定。分块传输不要求每块重复查链，但重新封装、重试投递须复核当前登记，不能直接沿用旧信封。该规则依赖 RPC 提供的链视图，不能消除读链后更新的竞态，也不能保证全网即时切换。

轮换公钥影响后续密钥封装，不会撤销旧私钥解密已有密文的能力，也不会撤销设备发帖或 NAS 服务签名授权。希望排除旧持钥者时，后续新内容必须使用新的随机内容密钥，不能继续复用对方已经获得的对称密钥。旧私钥按指纹作为历史解密材料保留，或明确接受旧内容不可读；迁移与清理策略另定。具体候选流程见[通信草案第 10 节](node-communication-protocol-v0.1.md#103-公钥轮换与加密前读取候选流程)。

## 7. 社交通信分类及既定行为

| 通信类型 | 示例 | 可靠性方向 |
| --- | --- | --- |
| 控制请求 | 身份验证、查询节点、建立中继通道 | 请求响应、超时和明确失败，报文待定 |
| 社交事件 | 关注、发帖通知、点赞；后续评论与聊天 | 持久化、去重、接收方保存确认、重试 |
| 内容传输 | 图片、视频、文件 | 校验完整性，分块、取消及断点续传细节待定 |

已确认的行为：

- 逻辑目标是接收方 NAS，物理路径可直连或经中继，不要求帖子先推给中继。
- 用户签署帖子和附件清单并明确确认发布内容及范围，自己的 NAS 验证并持久化内容、附件及发布确认后才推送；App 离线后继续投递，并为其他有权限的用户提供内容服务。仅签名或保存不构成发布许可，NAS 不得自主发布或签署新用户帖子；本地文本 API 已用独立 `SocialAction.Publish` 和一次性挑战表达发布确认，跨节点凭据复核仍待设计。
- 首期发送方保存待投递任务，双方 NAS 需要有同时在线时间；中继不默认提供离线信箱。
- 中继收到不等于目标持久化；正文保存、附件下载、用户已读分开处理。
- 帖子不能远程撤回。关注者默认保存可访问的正文，附件按需获取，收藏完整保存至自己的 NAS。
- 发布及接收遵守可见范围、授权和黑名单规则；互动为独立签名事件，最终同步，重试不能重复计数。

## 9. 设计场景检查

以下为后续实现的检查依据，不表示已运行测试。

| 场景 | 预期 |
| --- | --- |
| 首次登记 | 钱包登记本人地址、NAS PeerId、加密公钥和昵称，其他钱包不能覆盖 |

| 头像或性别获取 | 从链下获取，验证来源并遵守用户可见范围，不写入合约 |
| 中继不可达 | 刷新登记及链下线索，失败显示不可达，不判断用户不存在 |
| 旧链下记录重放 | 按待定的版本、有效期及撤销机制拒绝，具体报文和测试待设计 |

## NAS 钱包登录接口（已实现首期）

Web 与原生 App 共用 EOA SIWE 挑战签名，NAS 使用 SQLite 保存挑战和会话哈希。Web 使用 HttpOnly Cookie，并校验自定义头及请求 Origin；原生 App 可使用 Bearer 会话，不要求 Origin。消息仍绑定服务配置的 domain、URI 和 Base Sepolia Chain ID。接口、资源限制及兼容性边界见[钱包登录](wallet-login.md)。该本地登录不替代本文的常驻 NAS 绑定查询、P2P 对端身份验证或服务密钥授权；Web 已接入用户明确确认的首次登记及钱包 provider 查询，见[首次绑定 NAS](nas-registration.md)；该流程不替代 P2P 对端验证或后续受保护内容接口授权。

首期实现补充：NAS 持久化 Ed25519 节点密钥并通过认证接口提供 PeerId；Web 由用户主动准备 NAS 持有的 X25519 公钥，然后由钱包签署 `register`。两区块确认及字段核对后显示登记成功，具体备份、恢复和 P2P 能力限制见[首次绑定 NAS](nas-registration.md)。
