## 1. 文档目的与约定

本文整理已讨论的产品行为、首期边界和验收依据，供后续通信协议、技术设计及开发任务引用。本文不是已交付功能清单，也不定义具体网络报文、密码算法或智能合约接口。当前代码仍处于原型阶段，本地文本发帖实现及限制见[发帖说明](posting.md)。

需求使用以下标记；“已确认”表示产品方向已确认，不表示代码已经实现：

| 标记 | 含义 |
| --- | --- |
| 已确认 | 已经确认的产品要求 |
| 建议 | 提议采用，但仍需确认或技术验证 |
| 待定 | 尚不能作为实现约束，需后续讨论 |
| 首期 | 最小社交闭环的目标 |
| 后续 | 首期不要求交付 |

功能需求使用 `FR`，质量需求使用 `QR`，待定问题使用 `OPEN`，验收场景使用 `AC`。各表的阶段和状态适用于该行全部要求。本文与早期 README、协议草案不一致之处，应结合需求状态识别为后续讨论结论或尚待解决的差异，不将技术设想视为定案。

## 2. 产品目标、角色与范围

### 2.1 产品定位

红叶将家庭 NAS 及其他设备连接为去中心化社交网络。用户以钱包身份参与，使用可信的常驻 NAS 保存内容、持续收发信息，通过关注自主选择接收内容。NAS 可以长期在线，手机 App 无需持续运行。

| 编号 | 状态 | 阶段 | 要求 |
| --- | --- | --- | --- |
| FR-001 | 已确认 | 首期 | 正式客户端方向为手机 App；Web 用于早期验证和 NAS 本地管理。早期 Web 验证不等同于完成正式 App 交付。 |
| FR-002 | 已确认 | 首期 | 验证钱包身份绑定、设备授权、NAS 组网、关注、发帖、内容获取及互动同步的最小闭环。 |
| FR-003 | 已确认 | 首期 | 不提供系统内容推荐算法；以用户主动关注和获取内容为主要入口。 |
| FR-004 | 已确认 | 后续 | 支持用户分享、整理和推荐内容，其他用户通过关注整理者获取推荐；分享不得扩大原内容访问权限，须区分原作者与分享者。首期是否包含分享操作待定。 |
| FR-005 | 已确认 | 后续 | 真实资金结算、第三方离线信箱、直播和数字资产交易不纳入首期交付。 |

### 2.2 产品角色

| 角色 | 职责与边界 |
| --- | --- |
| 用户／创作者 | 管理身份和设备，发布、阅读、关注及参与互动 |
| 常驻 NAS（盒子） | 可信地保存用户数据及应用解密私钥，处理获授权明文；仅对用户已签名并确认发布的内容持续投递，并向有权限的用户提供内容服务；在 App 离线后继续接收和同步 |
| 手机 App | 提供正式交互入口，持有设备私钥，发起并签署用户操作 |
| 本地管理 Web | 支持 NAS 配置与早期功能验证；具体管理权限另行设计 |
| 接入中继 | 提供公网可达入口，转发 App 与 NAS 之间的密文，不因转发而获得用户数据访问权 |
| 存储及公开服务提供方 | 后续提供托管或公开接入服务；不默认属于用户可信的家庭 NAS |

## 3. 身份、授权与信任

| 编号 | 状态 | 阶段 | 要求 |
| --- | --- | --- | --- |
| FR-010 | 已确认 | 首期 | 区分钱包身份、App 设备签名身份、NAS 节点身份、每用户应用加密密钥及 NAS 服务签名密钥；不得用一个节点身份代替所有家庭成员身份，也不得混用解密与签名权限。 |
| FR-011 | 已确认 | 首期 | 一个 NAS 支持多个用户，分别管理数据、设备、授权和密钥，普通用户不得读取或操作其他成员的私密数据。每用户应用密钥的私钥保存在可信 NAS 盒子，公钥登记到链上 `encryptionPublicKey` 字段；NAS 可主动使用该应用私钥解密针对对应公钥加密的、用户有权接收的内容或内容密钥，无需浏览器／App 在线逐次解密。私钥不得通过普通 API、日志、公开消息或链上泄漏。用户信任 NAS 本身，不承诺对 NAS 系统管理员隐藏明文；当前保管实现需手工备份主密钥及每用户密钥文件，自动备份／恢复界面尚未实现。 |
| FR-012 | 已确认 | 首期 | 钱包私钥不交给 NAS；NAS 社交授权用途受限且可撤销，不能据此支付、转账或授权其他设备。 |
| FR-013 | 已确认 | 首期 | 用户发帖内容由用户授权的客户端签署，并由用户明确确认发布；仅有签名或已保存内容不构成发布许可，NAS 不得自主发布。用户签名并确认发布、NAS 校验及持久化成功后，NAS 可在 App 离线后持续向目标用户推送该内容，并向其他有权限的用户提供正文及附件服务。NAS 不得独立创作、修改或冒充用户签署帖子。 |
| FR-014 | 已确认 | 首期 | 区分用户操作签名和 NAS 投递、同步等服务操作签名。用户行为由授权客户端发起，NAS 不得把自主投递解释为新增用户行为的许可。 |
| FR-015 | 已确认 | 首期 | App 与自己的 NAS 互相验证身份并建立加密通信；第三方中继不得读取私密请求、访问凭据和正文，也不得替换身份或篡改内容。 |
| FR-016 | 建议 | 首期 | 首次在家庭内网通过配对确认 NAS 和设备身份；每台设备可单独授权和撤销，更换中继不改变 App 信任的 NAS 身份。具体配对及恢复流程待定。 |
| FR-017 | 已确认 | 首期 | 撤销授权不触发已传播帖子的删除；已知撤销后拒绝不再具备权限的后续操作。历史事件的有效性判断规则另行确定。 |
| FR-018 | 已确认 | 首期 | 用户钱包控制本人的 NAS PeerId、内容加密公钥和昵称登记；NAS 服务授权不能代替钱包修改。更换、撤销和旧授权失效机制待设计，不再沿用链上服务密钥及授权代次作为已确认字段。 |
| FR-019 | 已确认 | 首期 | 当前所有链上功能统一使用 Base Sepolia（Chain ID `84532`）；NAS 通过可配置 RPC 访问链，不要求运行 L2 验证全节点。长期自建 L2 和代币方案另行设计，不改变后续功能排期。 |

术语约定：“用户应用密钥”指 FR-011 的内容加密／解密密钥对，其公钥就是链上内容加密公钥，不增加链上字段。它与客户端发帖签名密钥、NAS 节点密钥及服务签名密钥用途独立；NAS 能解密不代表能代用户签名、确认发布或扩大可见范围。

## 4. 核心流程与功能要求

### 4.1 接入与持续运行

| 编号 | 状态 | 阶段 | 要求 |
| --- | --- | --- | --- |
| FR-020 | 已确认 | 首期 | 家庭内网允许客户端直接访问 NAS；外网通过 NAS 主动建立的中继连接访问，不以家庭 NAS 具有公网入站地址为前提。 |
| FR-021 | 建议 | 首期 | NAS 预设接入中继及备用入口，主动连接并在断线后重连；发现、切换及连接指令授权协议另行设计。全部入口失效时，应明确显示不可达，不能承诺远程即时唤起。 |
| FR-022 | 已确认 | 首期 | App 退出或手机离线不停止 NAS 的接收、保存、获授权解密及同步任务，也不停止已由用户签名并确认发布的内容投递和授权内容服务；不能因此启动未获发布确认的内容传播。 |
| FR-023 | 已确认 | 首期 | 发送方 NAS 仅为用户已签名并确认发布的内容持久化待投递事件并重试，重启不丢失发布确认及待投递状态；首期需双方 NAS 存在同时在线的时间，不依赖第三方代存消息。 |
| FR-024 | 已确认 | 首期 | 区分传输收到和接收方持久化成功；不能仅因中继收到字节就向用户宣称目标 NAS 已保存。 |
| FR-025 | 已确认 | 首期 | 以钱包地址查询链上注册记录，取得对应 NAS PeerId、内容加密公钥及昵称；通过链下网络获取连接线索，具体发现协议待定。用户发现不依赖面对面扫码或用户链接，设备首次配对另行设计。 |
| FR-026 | 已确认 | 首期 | 链上用户信息仅存钱包地址、对应 NAS PeerId、内容加密公钥和昵称；头像（含地址、内容标识及哈希）、性别及其他资料通过链下网络获取。中继入口与服务授权改为链下设计。私钥、访问令牌、明文内容密钥和家庭 IP 不上链，查到登记不代表 NAS 在线。 |
| FR-027 | 待定 | 首期 | 链下中继入口与 NAS 服务授权需定义发布、签名、钱包授权、版本、防重放及撤销机制；旧草案的服务密钥发送链上入口更新交易不再作为已确认方案。 |
| FR-028 | 已确认 | 首期 | 区分交易提交、执行和节点获知状态更新；缓存不保证即时刷新。链确认、缓存期限、重组及旧服务授权失效机制待定，RPC 读取失败不能解释为用户未注册。 |

### 4.2 关注、发布与获取

| 编号 | 状态 | 阶段 | 要求 |
| --- | --- | --- | --- |
| FR-030 | 已确认 | 首期 | 用户可关注其他用户，通过关注关系获取内容。接收方按用户选择的接收规则处理通知；黑名单用户的内容不得被动投递。原型支持签名关注／取消关注、跨节点同步、接收偏好及黑名单过滤；完整历史同步与取消关注后的远端副本管理待细化。 |
| FR-031 | 已确认 | 首期 | 用户向自己的 NAS 提交帖子及附件，签署内容并明确确认发布；NAS 验证签名、针对该内容及发布范围的发布确认，并持久化内容及确认状态后，才创建投递任务或向其他有权限的用户提供内容服务。未确认发布的已签名内容仅可作为本地保存内容，不得自动传播。上传、校验或保存失败不得显示发布成功。 |
| FR-032 | 已确认 | 首期 | 客户端分别显示保存至自己的 NAS、等待投递、目标已持久化等状态。没有明确目标的公开传播不得表述为“已送达全网”。 |
| FR-033 | 已确认 | 首期 | 已发布帖子不提供作者远程撤回功能；接收方保存的副本不受作者远程删除控制。作者本地副本的管理不等于撤回。 |
| FR-034 | 已确认 | 首期 | 关注者默认保存可访问的帖子正文；图片和视频按需拉取。免费全网广播帖属于公开内容，无需内容加密；定向帖必须加密。付费帖无论传播范围均增加付费加密层，付款前不得交付明文或付费密钥，公开预览不等于公开正文。获取受限正文及附件须符合原内容访问权限；传播范围包含全网广播、我关注的人、关注我的人、好友（互相关注）和指定的人，关系范围以用户签名时确认的接收名单为准。 |
| FR-035 | 已确认 | 首期 | 收藏将正文及附件完整保存到收藏者自己的 NAS；下载失败或权限不足时显示未完成，不得仅保存一个链接便宣称完整保存。 |
| FR-036 | 建议 | 首期 | 使用小型通知告知新内容，大附件按需拉取；“全网可见”不要求全网节点接收或保存副本。具体广播与订阅机制另行确定。 |
| FR-037 | 已确认 | 首期 | 用户可选择免费或付费帖，以及全网广播、我关注的人、关注我的人、好友（互相关注）或指定接收钱包（可从好友／关注列表选择或输入地址）。签名和发布确认必须绑定正文、价格和传播范围。定向内容先使用随机对称密钥加密，再将该密钥分别加密给接收者公钥，密文随帖子投递；不能向非目标用户扩大权限。 |
| FR-038 | 已确认 | 首期 | 付费内容额外使用独立内容密钥加密，智能合约只保存加密给作者 NAS 的密钥材料及价格／付款状态，不保存明文密钥。NAS 确认买家付款后，才将付费密钥重新封装给买家公钥并交付内容。定向付费帖同时检查受众及付款；合约不能保守秘密或自行重新加密，首版依赖作者 NAS 在线交付，原型仅使用 Base Sepolia 测试 ETH。 |
| FR-039 | 已确认 | 首期 | 用户可组合接收全网广播、我关注的人的帖子、关注我的人的帖子及明确发给我的帖子，多个选择按 OR 组合。接收偏好只控制被动接收，不替代内容访问权限或付费条件。默认接收我关注的人及明确发给我的内容，其他来源可主动开启。 |

支持标题加文字、标题加文字和图片、标题加图片、标题加视频、标题加文字和视频；文字在媒体帖中可选，图片最多 9 张或视频 1 个，不能混发。Web 采用封面卡片和媒体详情，个人资料统一从左下角钱包进入。本地上传及签名引用已实现，跨节点附件投递另行接入。

典型发布流程为：用户准备内容 → 用户签名并明确确认发布内容及范围 → 提交至自己的 NAS → NAS 校验签名和发布确认，持久化内容及确认状态 → 返回本地保存确认 → NAS 持续向目标用户投递，并为其他有权限的用户提供内容服务 → 接收方校验及持久化 → 返回目标保存确认。仅保存或签名不触发发布；签名与发布确认可以在同一次用户交互完成，不要求两个独立按钮。发布确认的协议表达及防重放细节另行设计，不把现有内容签名自动当作发布确认。附件是否已获取应独立于帖子正文的接收状态。

### 4.3 互动与最终同步

| 编号 | 状态 | 阶段 | 要求 |
| --- | --- | --- | --- |
| FR-040 | 已确认 | 首期 | 点赞及收藏采用独立链下签名事件关联帖子，不直接改写原帖。是否公开传播收藏事件须先确定收藏可见性。 |
| FR-041 | 已确认 | 首期 | 互动采用最终同步，不保证离线或网络分区期间各副本的计数实时一致；网络恢复且取得同一组有效事件后，展示结果应一致。 |
| FR-042 | 建议 | 首期 | 持帖且希望更新的 NAS 订阅互动，断线恢复后补拉；首期由作者 NAS 汇集和分发事件，作者 NAS 离线时跨节点汇总可延迟。拥有副本本身不意味着网络已知其位置或能立即向其推送。 |
| FR-043 | 已确认 | 首期 | 重复投递同一互动事件不得重复计数；签名证明行为来源，不代表一个钱包对应一个自然人，首期不承诺防止多身份刷赞。 |
| FR-044 | 已确认 | 后续 | 打赏资金采用链上结算凭据，互动记录关联对应帖子；未验证交易不得展示为已结算打赏。当前开发网络为 Base Sepolia，合约、确认与失败处理规则待定，首期不发生真实资金支付。 |

## 5. 质量要求与产品限制

| 编号 | 状态 | 阶段 | 要求 |
| --- | --- | --- | --- |
| QR-001 | 已确认 | 首期 | 任何私密读取和用户操作均校验身份、授权及用户边界，不以中继来源或声明的钱包地址替代认证。 |
| QR-002 | 已确认 | 首期 | 端到端保护 App 与 NAS 之间的私密通信，防止中继读取、替换或篡改；不自创密码算法。协议及算法选型留给安全通信设计。 |
| QR-003 | 已确认 | 首期 | 接收帖子、附件及事件时验证来源和完整性，篡改数据不得进入有效内容或互动统计。 |
| QR-004 | 已确认 | 首期 | 重试、重复及重放不导致重复执行；校验失败不得损坏已有有效状态。 |
| QR-005 | 已确认 | 首期 | 已确认持久化的数据及待投递任务能在正常进程重启后恢复；磁盘不足、保存失败等错误必须反馈，不能虚假确认成功。 |
| QR-006 | 已确认 | 首期 | 对输入大小、并发、缓存和重试施加资源限制，资源耗尽时可控失败。具体阈值、清理策略和目标 NAS 配置待验证。 |
| QR-007 | 已确认 | 首期 | 不在日志、公开消息或链上暴露私钥、明文内容密钥和私密内容；运行日志采用英文，状态应足以定位连接、投递及下载失败。 |
| QR-008 | 待定 | 首期 | 吞吐、延迟、支持设备及用户规模、存储上限、可用性和恢复时间目标，需根据目标硬件与原型测量确定，不预填性能承诺。 |

产品限制：

- 已交付给接收方的明文无法保证删除；加密不能防止已获授权的接收者另存或转发。
- 离线节点不能立即获知密钥撤销，历史签名如何判定仍需专门规则。
- 中继可以拒绝服务或观察连接时间、流量大小；正文加密不等于隐藏全部元数据。
- 首期没有第三方离线信箱，双方 NAS 从未同时在线时不能保证送达。
- Web 早期验证不能替代正式 App 的信任边界；由第三方提供的网页代码不能自动获得与独立发布 App 相同的安全结论。

## 6. 验收场景

以下是未来实现的验收依据，不表示这些检查已执行。包含待定规则的场景须先完成对应决策再进行最终验收。

| 编号 | 关联需求 | 场景与预期 |
| --- | --- | --- |
| AC-001 | FR-010～012、QR-001 | 在同一 NAS 绑定两名用户；用户 A 无法读取 B 的私密数据、使用 B 的密钥或执行 B 的操作；NAS 不保存钱包私钥。 |
| AC-002 | FR-015、020、QR-002 | 内网直接访问；外网在无家庭公网入站条件下经中继访问。受控中继不能读取私密请求及正文，替换身份或篡改密文应被拒绝。 |
| AC-003 | FR-013、022、031、QR-003 | 已上传并签名但未确认发布的内容，不产生投递任务，也不向其他用户提供正文或附件；用户针对该内容及范围确认发布并保存成功后退出 App，NAS 继续向目标用户投递，其他有权限的用户可获取内容，无权限用户被拒绝。发布确认及任务重启后仍有效；修改正文、附件清单或冒用其他内容的确认不能通过验证，NAS 不能生成有效的客户端发帖签名。 |
| AC-004 | FR-023、024、QR-005 | 接收方离线时保留待投递任务；发送方重启后任务仍在；双方恢复在线后完成投递并取得接收方持久化确认。 |
| AC-005 | FR-034、035 | 关注者自动保存正文，未请求的图片和视频不自动完整下载；收藏后完整保存，模拟附件不可用时显示未完成。 |
| AC-006 | FR-040～043、QR-004 | 同一互动重复投递不重复计数；多个持帖节点补齐同一组有效事件后结果一致；分区时允许显示暂时不同的结果。 |
| AC-007 | FR-017 | 节点获知撤销后拒绝已撤销设备的后续操作，已传播的合法历史帖子不被删除；历史事件判定以 OPEN-006 的最终规则为准。 |
| AC-008 | FR-031、032、QR-005 | 上传中断、磁盘不足或保存失败时不显示成功；中继收到数据但目标未确认时，不显示目标已保存。 |
| AC-009 | FR-003、004、034 | 首期内容来自主动关注而非系统推荐；后续分享受限帖子时，未获权限的接收者仍不能读取正文。 |
| AC-010 | FR-018、025～028 | 仅钱包可登记和修改本人的 NAS PeerId、公钥及昵称；头像、性别和中继入口等不写入链上用户记录。链下入口替换、旧授权和旧记录重放的验证方式待协议细化后验收。有效登记但中继不可达时显示连接失败，不判断为未注册。 |
| AC-011 | FR-010～012、022、QR-001、007 | 用户应用公钥登记在链上，对应私钥按用户保存在 NAS 盒子；浏览器／App 离线时，NAS 能解密针对该公钥加密的获授权内容，或先解封内容密钥再解密正文／附件。使用不匹配私钥应失败，普通 API、日志及链上不得暴露私钥；用户 A 不能调用 B 的私钥，解密成功不自动触发发布。 |
| AC-012 | FR-031、034、037 | 免费广播正文可公开读取，定向帖及所有付费帖的正文和标题保存在密文内；目标用户可以解密，非目标用户即使知道帖子 ID 也不能获取正文或对应密钥。修改内容、价格或受众使签名失效。 |
| AC-013 | FR-038 | 付费登记核对前不创建投递任务；未付款的目标用户拿不到正文或付费密钥，付款确认后可解锁，非目标用户付款也不扩大定向权限。同一买家不能重复购买，金额不符或作者收款失败不产生有效购买记录。合约公开存储不能被当作保密措施。 |
| AC-014 | FR-030、039 | 分别验证广播、关注及关注者来源和组合选择；关闭一个来源后仅通过其他仍匹配来源接收。接收范围不能使未获定向权限或未付款的用户读取内容，前端保持后端时间倒序。 |

## 7. 待定问题与后续设计入口

以下事项均为“待定”，不授权实现者自行选择产品规则。

| 编号 | 涉及阶段 | 问题与决策影响 |
| --- | --- | --- |
| OPEN-001 | 首期 | 收藏默认私密、公开还是用户可选？决定是否传播收藏事件、公开计数及下载行为的隐私边界。 |
| OPEN-002 | 首期 | 是否允许取消点赞、取消收藏？取消收藏是否删除本地附件？决定事件状态与存储管理。 |
| OPEN-003 | 首期／后续 | 帖子是否允许编辑或发布修订版？不得把编辑默认为撤回已传播副本。 |
| OPEN-004 | 后续 | 评论、聊天、群聊的具体范围、权限和首发时间；本文不定义其报文或交付承诺。 |
| OPEN-005 | 首期 | 首期支持哪些发布和接收范围、黑名单与分享如何组合，以及取消关注后的行为。 |
| OPEN-006 | 首期 | 撤销前签署但撤销后收到的事件如何判定？如何防止伪造签署时间？需明确有效性依据。 |
| OPEN-007 | 首期／后续 | 作者 NAS 不可用时，从哪些副本补齐互动和内容？是否采纳首期作者汇集方案，何时增加多来源同步？ |
| OPEN-008 | 首期 | 配对、设备遗失恢复、NAS 迁移、家庭管理员与成员权限、授权有效期的具体流程。 |
| OPEN-009 | 首期 | 已确定链上只登记钱包、NAS PeerId、加密公钥和昵称；中继入口及服务授权留在链下。仍待确定签名路由与发现、备用连接、持钥握手、授权与撤销、链确认／缓存／重组及费用授权边界。候选方案见[节点通信协议草案](node-communication-protocol-v0.1.md)，首期不接入真实资金。 |
| OPEN-010 | 首期 | 手机平台、App 技术路线、Web 验证交付边界及目标 NAS 硬件，须在排期前明确。 |
| OPEN-011 | 后续 | 当前链上开发网络已确定为 Base Sepolia，文本付费帖已有测试 ETH 合约原型；真实资金规则、打赏及流量结算的合约、确认及公平交付／退款机制，以及长期自建 L2 和代币迁移方案仍待确定，不将链下互动默认上链。 |
| OPEN-012 | 首期／后续 | 分享是否纳入首期，以及主题合集的数据形式与展示规则。 |
| OPEN-013 | 首期 | 本地图文／视频原型已用独立 `SocialAction` 的 `Publish` 动作绑定内容、价格、受众、NAS、一次性 nonce 及有效期，表达签名和明确发布确认；旧 `PublicEvent` 不自动构成发布许可。跨节点确认凭据传播及复核、附件与历史授权规则仍待网络阶段确定。 |

后续通信协议设计应引用需求编号，确定消息类型、签名对象、授权验证、确认语义、同步方式和错误处理。当前身份发现依赖 Base Sepolia 注册合约，不要求 NAS 运行链全节点或与链网络共用连接；详见[数据交换协议](data-exchange-protocol.md)。

后续讨论更新相关需求状态和阶段，保留编号，新增需求使用新编号；删除或替换需求时注明原因，不复用旧编号。重大调整同步记录到 [变更日志](../CHANGELOG.md)。需求确认、实现完成和测试通过是三个不同状态，验收证据应在实际开发后记录。
